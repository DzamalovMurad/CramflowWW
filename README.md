# CramFlow — Telegram Mini App цветочного магазина 🌸

MVP цветочного магазина внутри Telegram: один Go-сервис обслуживает и Mini App (API + статика React-сборки), и админ-бота. Заказы подтверждаются вручную — без онлайн-оплаты.

## Стек

- **Backend:** Go, GORM + PostgreSQL, миграции goose, `go-telegram-bot-api/v5` — один бинарник
- **Frontend:** React + TypeScript + Tailwind + Telegram WebApp SDK (Vite)
- **Хранение фото:** интерфейс `Storage` (`internal/storage`) — сейчас локальная папка / Railway Volume, легко заменить на S3/R2

## Структура

```
/cmd/main.go            — точка входа: HTTP-сервер + бот + миграции + graceful shutdown
/internal/model/        — GORM-модели
/internal/repository/   — доступ к БД
/internal/service/      — бизнес-логика (суммы заказов, промокоды)
/internal/handler/      — HTTP API (api.go), админ-бот (bot.go), заказ в чате (fallback.go),
                          рассылки, /stats, /stock, выгрузка CSV, канал, планировщик уведомлений,
                          лимитер отправок в Bot API (ratelimit.go)
/internal/storage/      — интерфейс Storage + локальная реализация
/internal/migrate/      — запуск миграций (goose)
/internal/backup/       — ночные дампы БД в Telegram-канал
/internal/observability/— Sentry и request id
/internal/ratelimit/    — token bucket для входящих запросов клиентского API
/migrations/            — SQL-миграции (единственный источник правды о схеме)
/web/                   — React-приложение (Home, Catalog, Product, Cart, Checkout, Confirmation)
```

## Переменные окружения

Полный список того, что читает код. Всё, чего нет в таблице, сервис игнорирует.
Столбец «если не задана» — не теория: это ровно то поведение, которое даёт код.

**Минимум для рабочего магазина:** `DATABASE_URL`, `BOT_TOKEN`, `ADMIN_IDS`,
`TELEGRAM_APP_URL`. Всё остальное имеет разумные значения по умолчанию.

| Переменная | Назначение | Если не задана |
|---|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL, например `postgres://user:pass@host:5432/db`. На Railway — reference `${{Postgres.DATABASE_URL}}` | **сервис не стартует:** `log.Fatal("DATABASE_URL не задан")` |
| `BOT_TOKEN` | токен бота от @BotFather | бот не запускается, сервис работает как чистый API + витрина (удобно для локальной разработки) |
| `ADMIN_IDS` | telegram_id админов через запятую (`123,456`): только им доступны команды, им же приходят карточки новых заказов | админ-команды недоступны никому, уведомления о заказах уходить некуда; в лог пишется предупреждение |
| `ADMIN_CHAT_ID` | один админ — устаревшая форма `ADMIN_IDS`, читается только когда `ADMIN_IDS` пуст | ничего, если задан `ADMIN_IDS` |
| `TELEGRAM_APP_URL` | публичный адрес Mini App (`https://xxx.up.railway.app`). Схему можно опустить — код допишет `https://` | Mini App не открыть: включается принудительный режим «заказ в чате» (`/order`), и `/fallback off` его не выключает |
| `CHANNEL_ID` | канал магазина: `@username` или числовой `-100…`. Бот должен быть в нём администратором | `/post` отвечает, что канал не настроен; блок «промокод за подписку» в Mini App не показывается |
| `PORT` | порт HTTP-сервера | `8080`. На Railway переменную подставляет платформа — вручную задавать не нужно |
| `WEB_DIST` | каталог собранного фронтенда | `./web/dist` (в образе переопределён на `/app/web/dist`) |
| `UPLOAD_DIR` | папка для фото товаров | `./uploads` (в образе `/app/uploads`). Без Railway Volume фото исчезнут при следующем деплое — тогда нужен `UPLOAD_STORE=db` |
| `UPLOAD_STORE` | `db` — хранить фото товаров в Postgres; любое другое значение — файлы в `UPLOAD_DIR` | `local`, то есть файлы на диске |
| `BOT_MODE` | `webhook` или `polling` | `polling`: бот сам опрашивает Telegram. Для Railway этого достаточно — контейнер не засыпает |
| `WEBHOOK_SECRET` | случайная строка: она же в пути webhook, она же в `secret_token` апдейтов | при `BOT_MODE=webhook` **сервис не стартует** (`log.Fatal`). При `polling` не используется |
| `PUBLIC_URL` | адрес сервиса для регистрации webhook | берётся `TELEGRAM_APP_URL`. Если пусты оба, а `BOT_MODE=webhook` — регистрация webhook падает с ошибкой |
| `BACKUP_CHANNEL_ID` | id приватного канала-архива для дампов БД (`-1001234567890`) | автобэкапы выключены, `/backup` отвечает «бэкапы не настроены» |
| `BACKUP_CRON` | расписание ночных дампов, 5 полей cron, UTC | `0 3 * * *` (03:00 UTC ежедневно). Некорректное выражение роняет сервис на старте — молча без бэкапов он не останется |
| `BACKUP_DIR` | где держать последние 14 дампов | `./backups` (в образе `/app/backups`) |
| `SENTRY_DSN` | DSN проекта Sentry | трекинг выключен, ошибки и паники только в логах (в лог пишется явная строка об этом) |
| `APP_ENV` | окружение в событиях Sentry | `production` |
| `RAILWAY_GIT_COMMIT_SHA` | версия релиза в Sentry | Railway подставляет сам; без него события просто без тега release |
| `TEST_DATABASE_URL` | база для интеграционных тестов (`go test ./internal/... -run Integration`) | интеграционные тесты пропускаются, обычный `go test` остаётся быстрым. В рантайме не читается |

## Миграции БД

Схему применяет [goose](https://github.com/pressly/goose): миграции лежат в `/migrations`
и **вшиты в бинарник** через `embed.FS`, поэтому рантайм-образу не нужны ни файлы, ни CLI.
Выбран goose, а не golang-migrate, потому что он запускается в процессе на уже открытом
`*sql.DB` и держит up и down в одном файле — это ровно текущая структура каталога.

`AutoMigrate` из продакшен-пути убран: единственный источник правды о схеме — SQL в `/migrations`.

```bash
# Миграции применяются автоматически при каждом старте сервиса — обычно делать ничего не нужно.

# Применить и выйти (например, разово перед первым деплоем)
DATABASE_URL=... go run ./cmd -migrate

# Посмотреть, что применено
DATABASE_URL=... go run ./cmd -migrate-status

# Откатить последнюю миграцию
DATABASE_URL=... go run ./cmd -migrate-down

# На Railway — той же командой в контейнере приложения
railway run ./cramflow -migrate-status
```

Текущая последовательность (применяется строго по возрастанию, каждый файл ровно один раз):

| Файл | Что добавляет |
|---|---|
| `00001_baseline.sql` | базовая схема: товары, варианты, фото, промокоды, клиенты, заказы, позиции, журнал статусов, «сегодня на базе», uploads |
| `00002_settings_and_badges.sql` | `settings` (переключатели рантайма), `products.low_stock` и `products.sort_order`, приведение `orders.is_anonymous` к `NOT NULL` |
| `00003_admin_bot.sql` | `products.is_available`, поля сегментации клиентов, `orders.source` / получатель, таблицы `broadcasts` и `broadcast_recipients` |
| `00004_photos_notifications_channel.sql` | `order_photos`, `notifications`, `claimed_bonuses`, `promo_codes.max_uses`, `users.acquisition_source` |

**Новая миграция:** создайте `migrations/00005_короткое_имя.sql` с секциями
`-- +goose Up` и `-- +goose Down`.

Первая миграция (`00001_baseline.sql`) повторяет схему, которую раньше создавал `AutoMigrate`,
и написана идемпотентно (`IF NOT EXISTS`). Поэтому она безопасно применяется и к пустой базе,
и к уже работающей проде: там она только отметится в `goose_db_version`. По той же причине
идемпотентны 00003 и 00004: их объекты на действующей проде мог успеть создать `AutoMigrate`
до перехода на goose.

## Шаг 1. Создание бота

1. Откройте [@BotFather](https://t.me/BotFather) → `/newbot` → задайте имя и username.
   Сохраните токен — это `BOT_TOKEN`.
2. Узнайте свой telegram_id (например, через [@userinfobot](https://t.me/userinfobot)) —
   он идёт в `ADMIN_IDS`.
3. `/setcommands` → выберите бота → вставьте список целиком:

   ```
   start - Открыть магазин
   order - Заказать в чате
   cancel - Прервать текущее действие
   help - Команды администратора
   orders - Заказы по статусам
   preorders - Предзаказы (доставка позже сегодня)
   clients - База клиентов (имя или телефон)
   stats - Сводка за период
   stock - Наличие товаров
   add - Добавить товар
   edit - Изменить товар
   hide - Скрыть/показать товар
   delete - Удалить товар
   fresh - Что сегодня свежее на базе
   post - Пост о товаре в канал
   broadcast - Рассылка по клиентам
   export - Выгрузка заказов в CSV
   fallback - Заказ через диалог бота (on|off)
   backup - Выгрузить дамп БД
   clean - Очистить историю чата
   done - Завершить приём фото
   ```

   Список общий: Telegram показывает одно меню всем. Первые три команды —
   клиентские, остальные админские, и вызвать их может только тот, чей id есть
   в `ADMIN_IDS` — остальным бот отвечает кнопкой «Открыть магазин».
   `/start` и `/cancel` работают в обеих ролях: для админа `/start` показывает
   тот же список, что и `/help`, а `/cancel` прерывает визард `/add` или `/edit`;
   для клиента `/cancel` отменяет начатый в чате заказ.

## Шаг 2. Деплой на Railway

Railway — единственный хостинг этого сервиса. Конфигов других платформ в
репозитории нет намеренно: два описания одного деплоя всегда расходятся.
Всё, что нужно платформе, лежит в `railway.toml` и `Dockerfile`.

1. [railway.app](https://railway.app) → **New Project → Deploy from GitHub repo** →
   выберите этот репозиторий. Сборка пойдёт по `Dockerfile` (`railway.toml`,
   `builder = "dockerfile"`), Nixpacks не используется: образу нужен `pg_dump`.
2. **+ New → Database → PostgreSQL** — Railway поднимет сервис БД.
3. Сервис приложения → **Variables**, минимальный набор:
   - `DATABASE_URL` → `${{Postgres.DATABASE_URL}}` (reference на сервис БД)
   - `BOT_TOKEN` и `ADMIN_IDS` — из шага 1
   - `TELEGRAM_APP_URL` — заполните после шага 4
4. **Settings → Networking → Generate Domain** — получите адрес вида
   `https://xxx.up.railway.app` и впишите его в `TELEGRAM_APP_URL`.
5. **Settings → Volumes → Add Volume**, mount path `/app/uploads` — иначе фото
   товаров исчезнут при следующем деплое. Альтернатива без Volume —
   `UPLOAD_STORE=db` (фото лягут в Postgres).
6. По желанию: `BACKUP_CHANNEL_ID` (ночные дампы, см. «Бэкапы») и `SENTRY_DSN`.

Полный список переменных со значениями по умолчанию — в разделе
«Переменные окружения» выше.

Миграции применяются самим бинарником при старте, отдельного release-шага нет:
в логах деплоя видно `goose: successfully migrated database to version: N`.

### Что задаёт `railway.toml`

| Параметр | Значение | Почему так |
|---|---|---|
| `builder` | `dockerfile` | образу нужен `pg_dump` для бэкапов, Nixpacks его не ставит |
| `startCommand` | `./cramflow` | схему поднимает сам бинарник, отдельная миграционная команда не нужна |
| `healthcheckPath` | `/healthz` | глубокая проба: БД, Bot API и версия схемы |
| `restartPolicyType` | `on_failure`, до 10 попыток | падение процесса — баг; лимит не даёт упавшему деплою крутиться в цикле |
| `numReplicas` | `1` | планировщик уведомлений, крон бэкапов и очередь рассылок рассчитаны на одного исполнителя |

### Healthcheck

| Путь | Что проверяет | Кому |
|---|---|---|
| `/healthz` | ping БД + доступность Bot API (`getMe`, ответ кэшируется на минуту) + версия схемы | Railway (`railway.toml`) |
| `/api/health` | только что процесс жив, БД не трогает | внешние пинги |

`/healthz` отвечает 503 только при недоступной БД: без неё сервис бесполезен и контейнер
надо перезапускать. Если лежит Telegram, ответ остаётся 200 со `status: degraded` —
витрина при этом работает, и передеплой ничего не починит. Проба идёт мимо лимитера
клиентского API — иначе она блокировала бы сама себя.

### Остановка

По `SIGTERM` (деплой, рестарт) сервис перестаёт принимать новые запросы, доводит до конца
текущие, дожидается начатых отправок бота и только потом закрывает соединения с БД —
клиент не увидит обрыва на оформлении заказа. На всё отводится 20 секунд.
Долгие фоновые задачи в этот бюджет не лезут: рассылка и планировщик уведомлений
выходят из цикла по сигналу и продолжают после рестарта с того места, где остановились.

## Шаг 3. Подключение Mini App

В @BotFather:
1. `/setdomain` → выберите бота → отправьте домен приложения (`xxx.up.railway.app`).
2. **Bot Settings → Menu Button → Configure menu button** → вставьте `TELEGRAM_APP_URL` и название, например «Магазин». Теперь Mini App открывается кнопкой меню в чате с ботом.

## Шаг 4. Сидинг тестовых данных

Наполняет пустую БД 7 товарами (фото — в `web/public/seed/`) и промокодами `WELCOME10` (−10%) и `FLOWERS15` (−15%). Повторный запуск ничего не дублирует.

```bash
# локально
DATABASE_URL=... go run ./cmd -seed

# на Railway: одноразовая команда в сервисе приложения
railway run ./cramflow -seed
```

## Локальная разработка

```bash
# 1. PostgreSQL (любой способ; например docker)
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=cramflow postgres:16

# 2. Backend (порт 8080; без BOT_TOKEN бот просто не стартует)
export DATABASE_URL="postgres://postgres:dev@localhost:5432/cramflow?sslmode=disable"
go run ./cmd -seed   # один раз
go run ./cmd

# 3. Frontend в dev-режиме (порт 5173, /api проксируется на 8080)
cd web && npm ci && npm run dev

# Продакшен-сборка фронта (Go-сервер отдаёт web/dist сам)
cd web && npm run build
```

### Проверка перед деплоем

```bash
go build ./... && go vet ./... && go test ./...
cd web && npm run build && cd ..

# Интеграционные тесты репозитория (схему поднимают те же миграции, что и прод)
createdb cramflow_it
TEST_DATABASE_URL="postgres://postgres:dev@localhost:5432/cramflow_it?sslmode=disable" \
  go test ./internal/... -run Integration -count=1
```

### Репетиция чистого деплоя

Пустая база → миграции → старт → проба. Ровно то, что делает Railway:

```bash
createdb cramflow_fresh
export DATABASE_URL="postgres://postgres:dev@localhost:5432/cramflow_fresh?sslmode=disable"

go build -o /tmp/cramflow ./cmd
/tmp/cramflow -migrate         # goose: successfully migrated database to version: 4
/tmp/cramflow &                # без BOT_TOKEN — чистый API, бот не нужен
curl -s localhost:8080/healthz # {"bot":"skipped","db":"ok","status":"ok","version":4}
```

## Админ-бот

Команды работают только у тех, чей telegram_id есть в `ADMIN_IDS` (или в устаревшем
`ADMIN_CHAT_ID`), остальным бот показывает кнопку «Открыть магазин». Callback-кнопки
проверяются по тому же списку: payload можно подделать, права — нет.

- **/add** — визард: название → 4–5 фото → описание (или «-») → варианты одной строкой (`9 шт — 2990₽; 15 шт — 4490₽`) → категория → подтверждение. Товар сразу виден в Mini App.
- **/edit** — выбор товара → поле → новое значение. Помимо названия, описания, цен, категории
  и фото здесь же тумблеры бейджей: «⭐ Хит», «🔻 Мало осталось», «🏷 Скидка», «📦 Остаток»
  и «🔢 Порядок в хитах» (`sort_order` — им сортируется подборка в пустой корзине).
- **/hide** — скрыть/показать товар (с подтверждением). Скрытые товары не отдаются в каталог и не могут быть заказаны.
- **/delete** — удалить товар (с подтверждением).
- **/orders** — заказы по статусам с пагинацией; в карточке — «Подтвердить»,
  «Изменить статус», «Отменить» (с обязательной причиной) и «📷 Фото букета».
- **/preorders** — предзаказы: доставка позже сегодняшнего дня.
- **/clients `<имя или телефон>`** — поиск по базе клиентов и их заказам.
- **/stats** — сводка за период: выручка, заказы, средний чек, новые клиенты,
  топ товаров и разбивка по каналам привлечения (`orders.source`).
- **/stock** — наличие товаров: тумблер «есть/нет» отдельно от `/hide`.
  `is_hidden` — сезонное «убрать с витрины», `is_available` — сегодняшняя закупка;
  витрина требует обоих.
- **/fresh** — список свежего на сегодня. Из него же выводится бейдж «сезонный» на витрине.
- **/post `<id товара>`** — пост о товаре в канал `CHANNEL_ID` с кнопкой «Заказать».
- **/broadcast** — рассылка по сегменту (все / покупали / корзина без заказа).
  Аудитория и статус каждого адресата живут в БД, поэтому рассылка переживает
  рестарт и никому не пишет дважды.
- **/export** — выгрузка заказов за период в CSV.
- **/fallback on|off** — заказ через диалог бота (см. ниже).
- **/backup** — сделать дамп БД прямо сейчас и отправить в архивный канал.
- **/clean** — удалить служебную переписку бота в админ-чате.
- **/done** — завершить приём фото в визарде, **/cancel** — прервать текущее действие.
- Уведомление о каждом новом заказе приходит админам с теми же кнопками.

**Фото букета и уведомления клиенту.** Из карточки заказа админ присылает фото
собранного (или вручённого) букета — оно сохраняется на заказе и сразу уходит клиенту.
Смена статуса тоже уведомляет клиента, а через 2 часа после доставки бот спрашивает
«Как вам букет?»: ответ пересылается админам, а за первый отзыв клиент получает
одноразовый промокод. Очередь отложенных уведомлений живёт в БД, поэтому рестарт
сервиса их не теряет и не дублирует.

## Заказ в чате (fallback-режим)

Если Mini App недоступен — упал фронтенд, идёт долгий деплой, у клиента старый Telegram —
магазин не должен переставать продавать. В этом режиме заказ оформляется обычным диалогом:

```
/order → кнопки с 10 букетами → размер → количество → адрес → телефон → подтверждение
```

Заказ создаётся тем же кодом, что и из Mini App, поэтому в CRM, уведомлениях и статусах
он ничем не отличается от обычного (в комментарии помечено, что он из чата).

Включение:

- **`/fallback on`** — вручную, когда приложение лежит. **`/fallback off`** — обратно.
  Настройка живёт в БД и переживает рестарт контейнера.
- **Автоматически**, если `TELEGRAM_APP_URL` не задан: другого способа заказать просто нет,
  поэтому режим включён принудительно и `/fallback off` его не выключит.

Клиенту режим виден как кнопка «💬 Заказать в чате» рядом с «Открыть магазин», а экран ошибки
Mini App предлагает «открыть чат с ботом» — оттуда клиент попадает ровно сюда.

## Бэкапы

Ночью (по умолчанию 03:00 UTC, настраивается `BACKUP_CRON`) сервис делает `pg_dump`,
сжимает в gzip и отправляет документом в приватный канал `BACKUP_CHANNEL_ID`.
Telegram хранит файлы бессрочно — канал заодно и архив. Локально в `BACKUP_DIR`
остаются последние 14 дампов, остальные удаляются. Вручную — команда `/backup`.

**Настройка канала:** создайте приватный канал → добавьте бота администратором с правом
отправки сообщений → узнайте id канала (например, переслав сообщение из него в
[@userinfobot](https://t.me/userinfobot); он выглядит как `-1001234567890`) → впишите
в `BACKUP_CHANNEL_ID`. Если ночной дамп не удался, бот напишет об этом админам —
тишина в канале не должна выглядеть как «всё хорошо».

### Восстановление из дампа

```bash
# 1. Скачайте нужный .sql.gz из архивного канала (или возьмите из BACKUP_DIR)
# 2. Распакуйте
gunzip cramflow-2026-07-31-0300.sql.gz

# 3. Залейте в базу. Дамп сделан с --clean --if-exists: он сам удалит
#    существующие таблицы перед восстановлением, отдельно чистить базу не нужно.
psql "$DATABASE_URL" -f cramflow-2026-07-31-0300.sql

# 4. Догоните схему до текущей версии кода (если дамп старше последних миграций)
DATABASE_URL=... ./cramflow -migrate
```

Дамп создаётся с `--no-owner --no-privileges`, поэтому разворачивается в базу
любого хостинга — роли исходного сервера не требуются. Проверять восстановление
лучше на отдельной базе: `createdb cramflow_restore` и `psql` в неё.

### Промокоды (deep-link)

Ссылка вида `https://t.me/<бот>?start=WELCOME10` сохраняет код за пользователем; при оформлении заказа он применяется автоматически (и записывается в заказ). Код можно ввести и вручную на экране оформления — ручной ввод приоритетнее сохранённого. Промокоды создаются в БД:

```sql
INSERT INTO promo_codes (code, discount_percent, uses) VALUES ('SPRING20', 20, 0);
```

## Как менять дизайн и тексты

Всё вынесено в три места — компоненты трогать не нужно:

| Что меняем | Где |
|---|---|
| Цвета (обе темы), шрифты, радиусы, тени | `web/src/styles/index.css`, секция «ДИЗАЙН-ТОКЕНЫ» (CSS-переменные) |
| Все тексты интерфейса, подписи категорий и фильтров | `web/src/content.ts` |
| Шрифтовые файлы (woff2, self-hosted) | `web/public/fonts/` + `fonts.css` там же |
| Описания, цены, фото товаров | БД — через админ-бота `/add`, `/edit` |

Стиль: минимализм в духе премиальных ритейлеров — строчная типографика (Onest + JetBrains Mono, self-hosted), монохром с точечным лаймовым акцентом `#A7FC00`, фото на серых плитках `--c-tile`, тонкие линии. Тёмная тема — те же токены в `:root[data-theme='dark']`.

## Принятые решения (чего не было в спеке)

- **Фильтр «🚚 Доставка сегодня»** — отдаёт весь активный каталог: признака «доставка сегодня» у товара нет, магазин доставляет всё в тот же день. **«🔥 Популярное»** — сортировка по числу проданных единиц, **«🆕 Новинки»** — товары младше 14 дней, **«💰 До 3000 ₽»** — минимальный вариант ≤ 3000.
- **Идентификация покупателя** — по `initData` Telegram WebApp (подпись проверяется HMAC-SHA256). Запросы без валидной initData (например, из браузера при разработке) привязываются к общему «гостевому» пользователю с `telegram_id = 0`.
- **Цены хранятся в рублях целыми числами**; сумма заказа всегда пересчитывается на сервере по ценам из БД, клиентским данным сервер не доверяет. Скидка применяется к итогу с округлением вниз.
- **Название товара фиксируется в позиции заказа** (`order_items.product_name`), чтобы заказ читался даже после удаления товара.
- **Фото из бота сохраняются как JPEG** (как отдаёт Telegram); WebP-версии используются для сид-каталога. Конвертацию в WebP на загрузке можно добавить позже за интерфейсом `Storage`.
- **`users.promo_code_id`** — доп. поле сверх спеки: там живёт промокод, полученный по deep-link.
- **Статусы заказа:** `new → confirmed → assembling → photo_sent → delivering → delivered / cancelled`.
  Переходы — конечный автомат: только следующий шаг либо отмена из нетерминального статуса,
  никаких прыжков `new → delivered`.
- **Бейдж «сезонный» не хранится у товара.** Он выводится из `/fresh` («сегодня на базе»):
  товар считается сезонным, если его название делит корень (4 буквы) с позицией из списка —
  «пионы» находят «Пионовидный микс», но «розы» не цепляют «Розовые каллы». Бейдж пропадает
  сам, когда позиция уходит из списка, и его не нужно снимать вручную.
- **Два «мало осталось».** `stock` — число, бейдж «осталось N» появляется при остатке ≤ 5.
  `low_stock` — ручной тумблер для случая, когда флорист видит остаток на базе, но точное
  число в карточке не ведёт. Ручной флаг приоритетнее.
- **Два лимитера, и это разные вещи.** Входящий (`internal/ratelimit`) — token bucket
  по telegram id (по IP, если initData невалидна): 5 GET/с со всплеском до 30 и не больше
  5 заказов подряд. Цель — не дать одному клиенту выжать пул из 8 соединений к Postgres,
  а не бороться с DDoS. Исходящий (`handler/ratelimit.go`) — очередь к Bot API под лимит
  Telegram ~30 msg/s, с повтором на 429. Через него идут **все** отправки: уведомления,
  рассылки, посты в канал, выгрузки и дампы БД. Собственных лимитеров у подсистем нет
  намеренно — две независимые «страховки» считали бы одну и ту же квоту.
- **Подлинность апдейтов бота** подтверждается дважды: секрет в пути webhook и заголовок
  `X-Telegram-Bot-Api-Secret-Token` (сравнение постоянного времени).
