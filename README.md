# CramFlow — Telegram Mini App цветочного магазина 🌸

MVP цветочного магазина внутри Telegram: один Go-сервис обслуживает и Mini App (API + статика React-сборки), и админ-бота. Заказы подтверждаются вручную — без онлайн-оплаты.

## Стек

- **Backend:** Go, GORM + PostgreSQL, миграции goose, `go-telegram-bot-api/v5` — один бинарник
- **Frontend:** React + TypeScript + Tailwind + Telegram WebApp SDK (Vite)
- **Хранение фото:** интерфейс `Storage` (`internal/storage`) — сейчас локальная папка / Railway Volume, легко заменить на S3/R2

## Структура

```
/cmd/main.go            — точка входа: HTTP-сервер + бот + миграции + graceful shutdown
/internal/model/        — GORM-модели
/internal/repository/   — доступ к БД
/internal/service/      — бизнес-логика (суммы заказов, промокоды)
/internal/handler/      — HTTP API (api.go), админ-бот (bot.go), заказ в чате (fallback.go)
/internal/storage/      — интерфейс Storage + локальная реализация
/internal/migrate/      — запуск миграций (goose)
/internal/backup/       — ночные дампы БД в Telegram-канал
/internal/observability/— Sentry и request id
/internal/ratelimit/    — token bucket для клиентского API
/migrations/            — SQL-миграции (единственный источник правды о схеме)
/web/                   — React-приложение (Home, Catalog, Product, Cart, Checkout, Confirmation)
```

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | **обязательна.** PostgreSQL, например `postgres://user:pass@host:5432/db` |
| `BOT_TOKEN` | токен бота от @BotFather (без него сервис работает как чистый API) |
| `ADMIN_IDS` | chat_id админов через запятую: только им доступны команды, сюда приходят заказы |
| `ADMIN_CHAT_ID` | один админ (устаревший вариант `ADMIN_IDS`, поддерживается для совместимости) |
| `TELEGRAM_APP_URL` | публичный URL Mini App. **Не задан → заказы принимаются диалогом в боте** (см. «Заказ в чате») |
| `PORT` | порт HTTP-сервера (Railway подставляет сам, по умолчанию 8080) |
| `UPLOAD_DIR` | папка для фото (по умолчанию `./uploads`; на Railway — путь Volume) |
| `UPLOAD_STORE` | `db` — хранить фото в Postgres (хостинг без диска); иначе файлы в `UPLOAD_DIR` |
| `BOT_MODE` | `webhook` или `polling` (по умолчанию). Webhook нужен хостингам, засыпающим без трафика |
| `WEBHOOK_SECRET` | обязателен при `BOT_MODE=webhook`: секрет в пути и в `secret_token` апдейтов |
| `PUBLIC_URL` | публичный адрес сервиса для регистрации webhook (по умолчанию `TELEGRAM_APP_URL`) |
| `BACKUP_CHANNEL_ID` | id приватного канала для дампов БД. Не задан → автобэкапы выключены |
| `BACKUP_CRON` | расписание бэкапов в формате cron, UTC (по умолчанию `0 3 * * *`) |
| `BACKUP_DIR` | где держать последние 14 дампов (по умолчанию `./backups`) |
| `SENTRY_DSN` | DSN проекта Sentry. Не задан → ошибки только в логах |
| `APP_ENV` | окружение для Sentry (по умолчанию `production`) |
| `S3_ENDPOINT`, `S3_KEY`, `S3_SECRET` | зарезервировано для будущего S3/R2 (сейчас не используются) |

## Миграции БД

Схему применяет [goose](https://github.com/pressly/goose): миграции лежат в `/migrations`
и **вшиты в бинарник** через `embed.FS`, поэтому рантайм-образу не нужны ни файлы, ни CLI.
Выбран goose, а не golang-migrate, потому что он запускается в процессе на уже открытом
`*sql.DB` и держит up и down в одном файле — это ровно текущая структура каталога.

`AutoMigrate` из продакшен-пути убран: единственный источник правды о схеме — SQL в `/migrations`.

```bash
# Миграции применяются автоматически при каждом старте сервиса — обычно делать ничего не нужно.

# Применить и выйти (например, разово перед первым деплоем)
DATABASE_URL=... go run ./cmd -migrate

# Посмотреть, что применено
DATABASE_URL=... go run ./cmd -migrate-status

# Откатить последнюю миграцию
DATABASE_URL=... go run ./cmd -migrate-down

# На Railway — той же командой в контейнере приложения
railway run ./cramflow -migrate-status
```

**Новая миграция:** создайте `migrations/00003_короткое_имя.sql` с секциями
`-- +goose Up` и `-- +goose Down`. Нумерация сквозная, файлы применяются по возрастанию.

Первая миграция (`00001_baseline.sql`) повторяет схему, которую раньше создавал `AutoMigrate`,
и написана идемпотентно (`IF NOT EXISTS`). Поэтому она безопасно применяется и к пустой базе,
и к уже работающей проде: там она только отметится в `goose_db_version`.

## Шаг 1. Создание бота

1. Откройте [@BotFather](https://t.me/BotFather) → `/newbot` → задайте имя и username. Сохраните токен — это `BOT_TOKEN`.
2. `/setcommands` → выберите бота → вставьте:
   ```
   add - Добавить товар
   edit - Изменить товар
   hide - Скрыть/показать товар
   delete - Удалить товар
   orders - Последние заказы
   fresh - Что сегодня свежее на базе
   fallback - Заказ через диалог бота (on|off)
   backup - Выгрузить дамп БД
   order - Заказать в чате
   ```
   Команда `order` — клиентская: она нужна, когда Mini App недоступен (см. «Заказ в чате»).
3. Узнайте свой chat_id (например, через [@userinfobot](https://t.me/userinfobot)) — это `ADMIN_CHAT_ID`.

## Шаг 2. Деплой на Railway

1. Создайте проект на [railway.app](https://railway.app) → **Deploy from GitHub repo** → выберите этот репозиторий. Сборка идёт по `Dockerfile` автоматически.
2. **+ New → Database → PostgreSQL** — Railway создаст сервис БД.
3. В сервисе приложения → **Variables**:
   - `DATABASE_URL` → `${{Postgres.DATABASE_URL}}` (reference на сервис БД)
   - `BOT_TOKEN`, `ADMIN_CHAT_ID` — из шага 1
   - `TELEGRAM_APP_URL` — публичный URL приложения (появится после шага 4)
4. **Settings → Networking → Generate Domain** — получите URL вида `https://xxx.up.railway.app`. Впишите его в `TELEGRAM_APP_URL`.
5. (Рекомендуется) **Settings → Volumes → Add Volume**, mount path `/app/uploads` — чтобы фото товаров переживали редеплой.
6. (Рекомендуется) **Variables → `BACKUP_CHANNEL_ID`** — id приватного канала для ночных дампов БД (см. «Бэкапы»), и `SENTRY_DSN`, если подключаете мониторинг.

Приложение слушает `$PORT` (Railway подставляет автоматически). Миграции применяются при старте —
в логах деплоя видно `goose: successfully migrated database to version: N`.

### Healthcheck

| Путь | Что проверяет | Кому |
|---|---|---|
| `/healthz` | ping БД + доступность Bot API (`getMe`, ответ кэшируется на минуту) | Railway (`railway.toml`) |
| `/api/health` | только что процесс жив, БД не трогает | внешний keepalive-пинг |

`/healthz` отвечает 503 только при недоступной БД: без неё сервис бесполезен и контейнер
надо перезапускать. Если лежит Telegram, ответ остаётся 200 со `status: degraded` —
витрина при этом работает, и передеплой ничего не починит.

### Остановка

По `SIGTERM` (деплой, рестарт) сервис перестаёт принимать новые запросы, доводит до конца
текущие, дожидается начатых отправок бота и только потом закрывает соединения с БД —
клиент не увидит обрыва на оформлении заказа. На всё отводится 20 секунд.

## Шаг 3. Подключение Mini App

В @BotFather:
1. `/setdomain` → выберите бота → отправьте домен приложения (`xxx.up.railway.app`).
2. **Bot Settings → Menu Button → Configure menu button** → вставьте `TELEGRAM_APP_URL` и название, например «Магазин». Теперь Mini App открывается кнопкой меню в чате с ботом.

## Шаг 4. Сидинг тестовых данных

Наполняет пустую БД 7 товарами (фото — в `web/public/seed/`) и промокодами `WELCOME10` (−10%) и `FLOWERS15` (−15%). Повторный запуск ничего не дублирует.

```bash
# локально
DATABASE_URL=... go run ./cmd -seed

# на Railway: одноразовая команда в сервисе приложения
railway run ./cramflow -seed
```

## Локальная разработка

```bash
# 1. PostgreSQL (любой способ; например docker)
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=cramflow postgres:16

# 2. Backend (порт 8080; без BOT_TOKEN бот просто не стартует)
export DATABASE_URL="postgres://postgres:dev@localhost:5432/cramflow?sslmode=disable"
go run ./cmd -seed   # один раз
go run ./cmd

# 3. Frontend в dev-режиме (порт 5173, /api проксируется на 8080)
cd web && npm install && npm run dev

# Продакшен-сборка фронта (Go-сервер отдаёт web/dist сам)
cd web && npm run build
```

## Админ-бот

Команды работают только из чата `ADMIN_CHAT_ID`, остальным бот показывает кнопку «Открыть магазин».

- **/add** — визард: название → 4–5 фото → описание (или «-») → варианты одной строкой (`9 шт — 2990₽; 15 шт — 4490₽`) → категория → подтверждение. Товар сразу виден в Mini App.
- **/edit** — выбор товара → поле → новое значение. Помимо названия, описания, цен, категории
  и фото здесь же тумблеры бейджей: «⭐ Хит», «🔻 Мало осталось», «🏷 Скидка», «📦 Остаток»
  и «🔢 Порядок в хитах» (`sort_order` — им сортируется подборка в пустой корзине).
- **/hide** — скрыть/показать товар (с подтверждением). Скрытые товары не отдаются в каталог и не могут быть заказаны.
- **/delete** — удалить товар (с подтверждением).
- **/orders** — последние 10 заказов; в деталях — кнопки «Подтвердить», «Изменить статус», «Отменить».
- **/fresh** — список свежего на сегодня. Из него же выводится бейдж «сезонный» на витрине.
- **/fallback on|off** — заказ через диалог бота (см. ниже).
- **/backup** — сделать дамп БД прямо сейчас и отправить в архивный канал.
- Уведомление о каждом новом заказе приходит админам с теми же кнопками.

## Заказ в чате (fallback-режим)

Если Mini App недоступен — упал фронтенд, идёт долгий деплой, у клиента старый Telegram —
магазин не должен переставать продавать. В этом режиме заказ оформляется обычным диалогом:

```
/order → кнопки с 10 букетами → размер → количество → адрес → телефон → подтверждение
```

Заказ создаётся тем же кодом, что и из Mini App, поэтому в CRM, уведомлениях и статусах
он ничем не отличается от обычного (в комментарии помечено, что он из чата).

Включение:

- **`/fallback on`** — вручную, когда приложение лежит. **`/fallback off`** — обратно.
  Настройка живёт в БД и переживает рестарт контейнера.
- **Автоматически**, если `TELEGRAM_APP_URL` не задан: другого способа заказать просто нет,
  поэтому режим включён принудительно и `/fallback off` его не выключит.

Клиенту режим виден как кнопка «💬 Заказать в чате» рядом с «Открыть магазин», а экран ошибки
Mini App предлагает «открыть чат с ботом» — оттуда клиент попадает ровно сюда.

## Бэкапы

Ночью (по умолчанию 03:00 UTC, настраивается `BACKUP_CRON`) сервис делает `pg_dump`,
сжимает в gzip и отправляет документом в приватный канал `BACKUP_CHANNEL_ID`.
Telegram хранит файлы бессрочно — канал заодно и архив. Локально в `BACKUP_DIR`
остаются последние 14 дампов, остальные удаляются. Вручную — команда `/backup`.

**Настройка канала:** создайте приватный канал → добавьте бота администратором с правом
отправки сообщений → узнайте id канала (например, переслав сообщение из него в
[@userinfobot](https://t.me/userinfobot); он выглядит как `-1001234567890`) → впишите
в `BACKUP_CHANNEL_ID`. Если ночной дамп не удался, бот напишет об этом админам —
тишина в канале не должна выглядеть как «всё хорошо».

### Восстановление из дампа

```bash
# 1. Скачайте нужный .sql.gz из архивного канала (или возьмите из BACKUP_DIR)
# 2. Распакуйте
gunzip cramflow-2026-07-31-0300.sql.gz

# 3. Залейте в базу. Дамп сделан с --clean --if-exists: он сам удалит
#    существующие таблицы перед восстановлением, отдельно чистить базу не нужно.
psql "$DATABASE_URL" -f cramflow-2026-07-31-0300.sql

# 4. Догоните схему до текущей версии кода (если дамп старше последних миграций)
DATABASE_URL=... ./cramflow -migrate
```

Дамп создаётся с `--no-owner --no-privileges`, поэтому разворачивается в базу
любого хостинга — роли исходного сервера не требуются. Проверять восстановление
лучше на отдельной базе: `createdb cramflow_restore` и `psql` в неё.

### Промокоды (deep-link)

Ссылка вида `https://t.me/<бот>?start=WELCOME10` сохраняет код за пользователем; при оформлении заказа он применяется автоматически (и записывается в заказ). Код можно ввести и вручную на экране оформления — ручной ввод приоритетнее сохранённого. Промокоды создаются в БД:

```sql
INSERT INTO promo_codes (code, discount_percent, uses) VALUES ('SPRING20', 20, 0);
```

## Как менять дизайн и тексты

Всё вынесено в три места — компоненты трогать не нужно:

| Что меняем | Где |
|---|---|
| Цвета (обе темы), шрифты, радиусы, тени | `web/src/styles/index.css`, секция «ДИЗАЙН-ТОКЕНЫ» (CSS-переменные) |
| Все тексты интерфейса, подписи категорий и фильтров | `web/src/content.ts` |
| Шрифтовые файлы (woff2, self-hosted) | `web/public/fonts/` + `fonts.css` там же |
| Описания, цены, фото товаров | БД — через админ-бота `/add`, `/edit` |

Стиль: минимализм в духе премиальных ритейлеров — строчная типографика (Inter 400/500/700), монохром с точечным лаймовым акцентом `#A7FC00`, фото на серых плитках `--c-tile`, тонкие линии. Тёмная тема — те же токены в `:root[data-theme='dark']`.

## Принятые решения (чего не было в спеке)

- **Фильтр «🚚 Доставка сегодня»** — отдаёт весь активный каталог: признака «доставка сегодня» у товара нет, магазин доставляет всё в тот же день. **«🔥 Популярное»** — сортировка по числу проданных единиц, **«🆕 Новинки»** — товары младше 14 дней, **«💰 До 3000 ₽»** — минимальный вариант ≤ 3000.
- **Идентификация покупателя** — по `initData` Telegram WebApp (подпись проверяется HMAC-SHA256). Запросы без валидной initData (например, из браузера при разработке) привязываются к общему «гостевому» пользователю с `telegram_id = 0`.
- **Цены хранятся в рублях целыми числами**; сумма заказа всегда пересчитывается на сервере по ценам из БД, клиентским данным сервер не доверяет. Скидка применяется к итогу с округлением вниз.
- **Название товара фиксируется в позиции заказа** (`order_items.product_name`), чтобы заказ читался даже после удаления товара.
- **Фото из бота сохраняются как JPEG** (как отдаёт Telegram); WebP-версии используются для сид-каталога. Конвертацию в WebP на загрузке можно добавить позже за интерфейсом `Storage`.
- **`users.promo_code_id`** — доп. поле сверх спеки: там живёт промокод, полученный по deep-link.
- **Статусы заказа:** `new → confirmed → delivering → done / cancelled`.
- **Бейдж «сезонный» не хранится у товара.** Он выводится из `/fresh` («сегодня на базе»):
  товар считается сезонным, если его название делит корень (4 буквы) с позицией из списка —
  «пионы» находят «Пионовидный микс», но «розы» не цепляют «Розовые каллы». Бейдж пропадает
  сам, когда позиция уходит из списка, и его не нужно снимать вручную.
- **Два «мало осталось».** `stock` — число, бейдж «осталось N» появляется при остатке ≤ 5.
  `low_stock` — ручной тумблер для случая, когда флорист видит остаток на базе, но точное
  число в карточке не ведёт. Ручной флаг приоритетнее.
- **Лимиты клиентского API** — token bucket по telegram id (по IP, если initData невалидна):
  5 GET/с со всплеском до 30 и не больше 5 заказов подряд. Цель — не дать одному клиенту
  выжать пул из 8 соединений к Postgres, а не бороться с DDoS.
- **Подлинность апдейтов бота** подтверждается дважды: секрет в пути webhook и заголовок
  `X-Telegram-Bot-Api-Secret-Token` (сравнение постоянного времени).
